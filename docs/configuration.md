# Конфигурация и переменные окружения

Конфигурация сервера реализована в пакете [`internal/config`](../internal/config/config.go). При запуске функция `config.LoadFromOS()` сначала считывает файл `.env` из текущей рабочей директории (если он существует), а затем поверх него накладывает переменные окружения операционной системы. Переменные окружения ОС всегда имеют приоритет над `.env`.

Если хотя бы одна обязательная переменная отсутствует или не проходит валидацию, сервер немедленно завершает работу с перечислением всех обнаруженных ошибок конфигурации.

---

## 1. Основные параметры сервера и транспорта

| Переменная | Обязательна | По умолчанию | Описание |
| --- | :---: | --- | --- |
| `APP_URL` | **Да**\* | — | Публичный базовый URL сервера (Origin без пути, query-параметров и `#fragment`). Обязан использовать схему `https://`, за исключением локальных адресов (`http://localhost`, `http://127.0.0.1`, `http://[::1]`). Используется для формирования OAuth-метаданных и проверки заголовка `Origin`. (\*Не требуется при настройке `BITRIX_WEBHOOK_URL`). |
| `HOST` | Нет | `0.0.0.0` | IP-адрес или хост, на котором HTTP-сервер слушает входящие соединения. |
| `PORT` | Нет | `3000` | TCP-порт HTTP-сервера (`1`–`65535`). |
| `MCP_TRANSPORT` | Нет | `http` | Транспорт протокола MCP: `http` (Stateless Streamable HTTP на эндпоинте `/mcp`) или `stdio` (обмен через `stdin`/`stdout`). |
| `LOG_LEVEL` | Нет | `info` | Уровень логирования в `stderr`: `trace`, `debug`, `info`, `warn`, `error`, `fatal`, `silent`. |

## 2. База данных SQLite

| Переменная | Обязательна | По умолчанию | Описание |
| --- | :---: | --- | --- |
| `DATABASE_PATH` | Нет | `./data/bitrix24-mcp.sqlite` | Путь к файлу базы данных SQLite или `:memory:` для работы в оперативной памяти. |
| `DATABASE_URL` | Нет | — | Альтернативный алиас для `DATABASE_PATH` (используется только если `DATABASE_PATH` не задан). |

### Форматы пути SQLite
Функция `NormalizeSqlitePath` автоматически очищает префиксы `sqlite://`, `sqlite:`, `file://` и `file:`. Значения `:memory:` и `file::memory:...` нормализуются в `:memory:`. Для файловой базы автоматически создаются родительские директории (`0755`) и включаются прагмы `WAL`, `foreign_keys = ON` и `busy_timeout = 5000`.

## 3. Настройки подключения к Битрикс24 (OAuth и входящий вебхук)

Сервер поддерживает два режима авторизации на портале Битрикс24:
1. **Полноценный OAuth 2.0**: многопользовательский режим с автоматической ротацией токенов (`BITRIX_CLIENT_ID` + `BITRIX_CLIENT_SECRET` + `APP_URL`).
2. **Входящий вебхук (`BITRIX_WEBHOOK_URL`)**: упрощённый режим для локальной разработки, `stdio` и single-tenant окружений. При указании `BITRIX_WEBHOOK_URL` переменные `BITRIX_CLIENT_ID`, `BITRIX_CLIENT_SECRET` и `APP_URL` становятся необязательными, а подключение к порталу автоматически сидируется в SQLite на старте.

| Переменная | Обязательна | По умолчанию | Описание |
| --- | :---: | --- | --- |
| `BITRIX_WEBHOOK_URL` | Нет | — | URL входящего вебхука Битрикс24 в формате `https://<domain>/rest/<user_id>/<webhook_code>[/]`. Автоматически создаёт и активирует бессрочное подключение. |
| `BITRIX_CLIENT_ID` | **Да**\* | — | Идентификатор (`client_id` / `CODE`) OAuth-приложения Битрикс24 (\*не требуется при наличии `BITRIX_WEBHOOK_URL`). |
| `BITRIX_CLIENT_SECRET` | **Да**\* | — | Секретный ключ (`client_secret`) OAuth-приложения Битрикс24 (\*не требуется при наличии `BITRIX_WEBHOOK_URL`). |
| `BITRIX_OAUTH_URL` | Нет | `https://oauth.bitrix.info/oauth/token` | Базовый URL OAuth-сервера авторизации токенов Битрикс24 (также поддерживает `https://oauth.bitrix24.tech/oauth/token`). |
| `BITRIX_API_VERSION` | Нет | `auto` | Версия протокола REST: `auto` (REST 3.0 с прозрачным фоллбэком на Legacy REST v2 при 404 / `ERROR_METHOD_NOT_FOUND`), `v3` (только REST 3.0) или `v2` (только Legacy REST). |
| `BITRIX_PORTAL_DOMAIN` | Нет | — | Домен портала Битрикс24 (например, `company.bitrix24.ru` или кастомный домен коробочной версии). |

### Роль `BITRIX_PORTAL_DOMAIN`
1. **Автоматический редирект в MCP OAuth 2.1**: когда MCP-клиент проходит авторизацию через `/authorize`, сервер перенаправляет пользователя именно на этот портал. Если переменная не задана, сервер сможет определить портал автоматически только в том случае, если в базе уже есть ровно одно активное подключение.
2. **Белый список домена (Allowlist)**: по умолчанию сервер разрешает подключать любые облачные порталы вида `*.bitrix24.(com|ru|de|eu|ua|by|kz|...)`. Если `BITRIX_PORTAL_DOMAIN` задан, сервер разрешает работу **только** с этим конкретным доменом (что позволяет как жёстко ограничить сервер одним облачным порталом, так и подключить self-hosted / коробочный Битрикс24 на собственном домене по HTTPS).

## 4. Безопасность и режимы работы

| Переменная | Обязательна | По умолчанию | Описание |
| --- | :---: | --- | --- |
| `TOKEN_ENCRYPTION_KEY` | **Да** | — | Ключ для AES-256-GCM шифрования токенов Битрикс24 в SQLite. Должен представлять собой ровно **32 байта**, закодированных в `base64` (стандартном или raw) либо в виде **64 шестнадцатеричных символов (hex)**. |
| `MCP_AUTH_TOKEN` | **Да** | — | Статический Bearer-токен для аутентификации запросов к `/mcp`, `/oauth/bitrix/start` и `/oauth/bitrix/refresh`. Минимальная длина — **32 символа**. Сравнивается за константное время (`crypto/subtle`). |
| `BITRIX_MCP_DEFAULT_MODE` | Нет | `read_only` | Режим безопасности для новых подключений: `read_only` (разрешено только чтение) или `write_with_confirmation` (разрешена подготовка и подтверждение операций записи). |
| `BITRIX_MCP_ADMIN_TOOLS` | Нет | `false` | Булевый флаг (`true`/`1`/`yes` или `false`/`0`/`no`), сохраняемый в профиле подключения для разграничения административных возможностей политики безопасности. |

> **Важно:** Не меняйте `TOKEN_ENCRYPTION_KEY` на существующей базе данных без переавторизации порталов, иначе сервер не сможет расшифровать ранее сохранённые `access_token` и `refresh_token`.

## 5. Время жизни (TTL) токенов, состояний и кэша

Все значения задаются в секундах и должны быть положительными целыми числами (`>= 1`):

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `OAUTH_STATE_TTL_SECONDS` | `600` (10 мин) | Время жизни одноразового `state` при редиректе в OAuth Битрикс24. |
| `MCP_OAUTH_REQUEST_TTL_SECONDS` | `600` (10 мин) | Время жизни незавершённого запроса авторизации на экране согласия `/authorize` (и CSRF-куки). |
| `MCP_OAUTH_CODE_TTL_SECONDS` | `300` (5 мин) | Время жизни одноразового `authorization_code`, выдаваемого MCP-клиенту после входа в Битрикс24. |
| `MCP_OAUTH_ACCESS_TOKEN_TTL_SECONDS` | `3600` (1 час) | Время жизни `access_token`, выдаваемого MCP-клиенту эндпоинтом `/token`. |
| `MCP_OAUTH_REFRESH_TOKEN_TTL_SECONDS` | `2592000` (30 дней) | Время жизни `refresh_token` MCP-клиента (при каждом обмене происходит ротация). |
| `SCHEMA_CACHE_TTL_SECONDS` | `900` (15 мин) | Время актуальности кэша схемы Битрикс24 (типы сущностей, поля, воронки, стадии) в таблице `schema_cache`. |
| `PENDING_OPERATION_TTL_SECONDS` | `600` (10 мин) | Время, в течение которого подготовленная операция записи (`create_item`, `update_item`, `move_item_stage`) может быть подтверждена через `bitrix_confirm_operation`. |

## 6. Параметры REST-клиента Битрикс24

| Переменная | По умолчанию | Диапазон | Описание |
| --- | --- | --- | --- |
| `BITRIX_REQUEST_TIMEOUT_MS` | `15000` | `>= 1` | Таймаут одного HTTP-запроса к REST API и OAuth-серверу Битрикс24 в миллисекундах (15 секунд). |
| `BITRIX_MAX_RETRIES` | `3` | `0`–`8` | Максимальное число повторных попыток при сетевых сбоях, HTTP `429` / `5xx` и лимитах Битрикс24 (`QUERY_LIMIT_EXCEEDED`, `OPERATION_TIME_LIMIT`, `TOO_MANY_REQUESTS`). |
| `BITRIX_MAX_PAGES` | `20` | `1`–`100` | Максимальное количество страниц (по 50 элементов), выгружаемых за один вызов списочных методов (` CollectPages`). При значении `20` один поисковый запрос может собрать до `20 * 50 = 1000` записей. |

## 7. Настройка доверенных прокси (`TRUST_PROXY`)

Переменная `TRUST_PROXY` управляет тем, как сервер определяет IP-адрес клиента из заголовка `X-Forwarded-For` для работы Rate Limiter на OAuth-маршрутах (`/register`, `/authorize`, `/token`, `/revoke`):

| Значение `TRUST_PROXY` | Поведение |
| --- | --- |
| Не задано, `false`, `0`, `no` | Заголовок `X-Forwarded-For` игнорируется, используется непосредственный сетевой адрес `r.RemoteAddr`. |
| `true`, `yes` | Доверяет 1 обратному прокси (`Hops = 1`) — берётся последний адрес в `X-Forwarded-For`. |
| Целое число `N > 0` (например, `2`) | Доверяет `N` прокси-хопам с конца списка `X-Forwarded-For`. |
| Список IP / CIDR через запятую (например, `172.18.0.0/16, 10.0.0.1`) | Проверяет, что запрос пришёл от доверенного прокси, и выбирает первый справа адрес в `X-Forwarded-For`, не входящий в список доверенных подсетей. |

## 8. Логирование и автоматическая фильтрация секретов

Сервер пишет структурированные однострочные JSON-логи в поток `os.Stderr`:

```json
{"level":"info","message":"Server listening","address":"0.0.0.0:3000","time":"2026-11-08T00:00:00.000Z"}
```

Функция `config.RedactValue` рекурсивно обходит все поля логов и автоматически заменяет на `"[REDACTED]"` значения любых ключей из защищённого списка:
- `access_token`, `refresh_token`, `accessToken`, `refreshToken`
- `authorization`, `token`, `auth`
- `client_secret`, `bitrixClientSecret`
- `mcpAuthToken`, `tokenEncryptionKey`
- `code`, `code_verifier`

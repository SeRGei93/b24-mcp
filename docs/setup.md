# Настройка Битрикс24 и авторизация

В этом руководстве описано создание приложения в Битрикс24, способы авторизации портала на сервере, быстрый запуск через входящий вебхук (без туннелей) и совместное использование с официальным сервером `b24-dev-mcp`.

---

## 1. Создание локального приложения в Битрикс24

Сервер использует официальный OAuth 2.0 протокол Битрикс24. Чтобы получить `client_id` и `client_secret`:

1. В интерфейсе вашего портала Битрикс24 откройте:
   **Разработчикам** (`Developer resources`) → **Другое** (`Other`) → **Локальное приложение** (`Local application`).
2. Выберите тип приложения: **Серверное** (использует только REST API).
3. Заполните URL-адреса обработчиков (замените `https://your-server.example.com` на ваш публичный `APP_URL`):
   - **Путь вашего обработчика (`Handler path`)**:
     ```text
     https://your-server.example.com/oauth/bitrix/callback
     ```
   - **Путь для первоначальной установки (`Initial installation path`)**:
     ```text
     https://your-server.example.com/oauth/bitrix/install
     ```
4. В блоке **Права доступа (`Permissions / Scope`)** отметьте:
   - `CRM (crm)` — обязательно для работы со сделками, лидами, контактами, компаниями, предложениями и смарт-процессами.
   - `Пользователи (user)` — рекомендуется для инструмента `bitrix_list_users` и верификации профиля.
5. Нажмите **Сохранить** и скопируйте выданные:
   - **Код приложения** → `BITRIX_CLIENT_ID`
   - **Ключ приложения** → `BITRIX_CLIENT_SECRET`

## 2. Способы авторизации портала

Сервер поддерживает 4 способа привязки портала Битрикс24:

### Способ А: Автоматически через MCP OAuth 2.1 (рекомендуется для команд)
Подходит для клиентов с поддержкой интерактивного OAuth (Claude Code, Claude Desktop, Codex CLI):
1. Клиент инициирует подключение к `/mcp`.
2. В браузере открывается страница согласия MCP-сервера, а затем форма входа в Битрикс24.
3. После авторизации Битрикс24 возвращает токены на `/oauth/bitrix/callback`. Сервер шифрует их в SQLite и привязывает клиентскую сессию к полученному `connection.id`.

### Способ Б: Через установку в интерфейсе Битрикс24
В настройках созданного локального приложения внутри Битрикс24 нажмите кнопку **Установить** (или **Переустановить**):
- Портал отправит данные на эндпоинт `/oauth/bitrix/install`.
- Сервер проверит приложение через `app.info` и профиль пользователя через `profile.json`, сохранит подключение в базу и подтвердит установку (`BX24.installFinish()`).

### Способ В: Вручную со статическим токеном
Если используется статический токен `MCP_AUTH_TOKEN`, инициируйте OAuth-поток через браузер или cURL:

```bash
curl -i -H "Authorization: Bearer $MCP_AUTH_TOKEN" \
  "https://your-server.example.com/oauth/bitrix/start?domain=your-portal.bitrix24.ru&mode=write_with_confirmation"
```

Перейдите по ссылке из заголовка `Location` в браузере и завершите авторизацию. Сервер вернёт JSON с `connection.id`.

### Способ Г: Входящий вебхук (`BITRIX_WEBHOOK_URL`) без туннелей (Zero-Tunnel Setup)

Идеально подходит для локальной разработки, CLI-ассистентов и транспорта `stdio`, когда сервер не имеет публичного белого IP-адреса и не используются туннели (ngrok / Cloudflare Tunnel / localtunnel):

1. В интерфейсе Битрикс24 откройте: **Разработчикам** → **Другое** → **Входящий вебхук**.
2. В блоке **Настройка прав** выберите права:
   - `CRM (crm)`
   - `Пользователи (user)`
3. Скопируйте выданный вебхук (вид: `https://company.bitrix24.ru/rest/1/abcdefghijklmnop/`).
4. Укажите его в `.env`:
   ```dotenv
   BITRIX_WEBHOOK_URL=https://company.bitrix24.ru/rest/1/abcdefghijklmnop/
   BITRIX_MCP_DEFAULT_MODE=write_with_confirmation
   ```
5. При старте сервер автоматически сидирует активное подключение в SQLite, не требуя ни `APP_URL`, ни `BITRIX_CLIENT_ID`, ни `BITRIX_CLIENT_SECRET`.

## 3. Управление версиями REST API (`BITRIX_API_VERSION`)

Сервер поддерживает интеллектуальное управление протоколами Bitrix REST:
- `BITRIX_API_VERSION=auto` (по умолчанию): сервер выполняет запросы по протоколу REST 3.0 (`/rest/api/crm.<slug>.*`), обеспечивая пагинацию до 1 000 записей за один запрос, dot-notation реляционные выборки и агрегации `crm.<slug>.aggregate`. Если портал (например, коробочная версия On-Premise) возвращает 404 или `ERROR_METHOD_NOT_FOUND`, сервер автоматически переключается на Legacy REST v2 (`/rest/crm.item.*`) и кэширует режим `v2` в SQLite.
- `BITRIX_API_VERSION=v3`: форсирует только REST 3.0 без фоллбэка.
- `BITRIX_API_VERSION=v2`: принудительно направляет все вызовы на Legacy REST v2 (для стабильной работы со старыми On-Premise установками).

## 4. Контроль мутаций и удаление (`bitrix_prepare_delete_item`)

Сервер реализует строгий двухэтапный конвейер любых мутаций данных (Human-in-the-loop):
1. **Подготовка (`prepare_*`)**:
   - `bitrix_prepare_create_item`
   - `bitrix_prepare_update_item`
   - `bitrix_prepare_move_item_stage`
   - `bitrix_prepare_delete_item` — подготовка удаления элемента CRM.
2. При вызове подготовки операция записывается в таблицу `pending_operations` SQLite в статусе `pending` и генерирует уникальный `operationId`. Вся полезная нагрузка (поля `UF_CRM_*`, идентификаторы) нормализуется заранее.
3. Клиент/пользователь просматривает параметры операции и вызывает `bitrix_confirm_operation` с полученным `operationId`.
4. Сервер атомарно клеймит операцию (`UPDATE status='executing' WHERE status='pending'`), отправляет запрос в Битрикс24 с HTTP-заголовком `Idempotency-Key: <operationId>` и сохраняет результат в аудит-лог.

## 5. Совместное использование с официальным сервером `b24-dev-mcp`

Официальный сервер Битрикс24 [`b24-dev-mcp`](https://mcp-dev.bitrix24.tech/mcp) и данный сервер решают взаимодополняющие задачи:

| Характеристика | Официальный `b24-dev-mcp` | Данный сервер (`bitrix24`) |
| --- | --- | --- |
| **Основное назначение** | Документация API, схемы методов, справка SDK | Живое управление CRM портала, автоматизация |
| **Чтение данных** | Справочные каталоги | REST 3.0 выборка, фильтрация, dot-notation, агрегаты |
| **Запись данных** | Отсутствует | Двухэтапные мутации, `Idempotency-Key`, аудит |
| **Авторизация** | Не требуется (публичный контекст) | OAuth 2.0 / 2.1, вебхуки, шифрование токенов |

### Настройка в Cursor / Windsurf / Claude Desktop
Добавьте оба сервера в конфигурационный файл:

```json
{
  "mcpServers": {
    "bitrix24": {
      "url": "https://your-server.example.com/mcp",
      "headers": {
        "Authorization": "Bearer <MCP_AUTH_TOKEN>"
      }
    },
    "b24-dev": {
      "url": "https://mcp-dev.bitrix24.tech/mcp"
    }
  }
}
```

## 6. Управление токенами и безопасность

- **Шифрование AES-256-GCM**: токены доступа и обновления Битрикс24 (`access_token`, `refresh_token`) никогда не сохраняются в открытом виде. Они шифруются симметричным ключом `TOKEN_ENCRYPTION_KEY` перед записью в SQLite.
- **Автоматическое обновление (`TokenManager`)**:
  - Токены Битрикс24 действуют 1 час. Сервер автоматически обновляет их упреждающе (если до истечения осталось менее 60 секунд) или реактивно (при получении ошибки `expired_token` от API).
  - Параллельные запросы к одному порталу дедуплицируются (Singleflight), чтобы не дублировать запросы на обновление.
- **Изоляция подключений (Connection Scoping)**:
  - Токены, выпущенные через MCP OAuth 2.1, привязаны к конкретному профилю Битрикс24. Клиент видит только своё подключение и не может совершать операции от лица других подключений.
  - Статический токен `MCP_AUTH_TOKEN` является административным и позволяет работать с любыми подключениями в БД, явно указывая `connectionId`.
